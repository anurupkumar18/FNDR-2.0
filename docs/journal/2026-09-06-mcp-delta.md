# 2026-09-06: fndr.delta, and the eighth tool

## Decision

`fndr.delta` answers "what happened since I last asked" from
`Store::changes_since`: how many records were captured at or after an
instant, the newest instant among them, and the busiest apps. Counts only,
like `fndr.timeline`; an agent that wants content follows up with
`fndr.search` or `fndr.source_evidence`.

This is the eighth ADR-007 tool, which meets that ADR's action item 1
("month 2, first 8 tools") by count.

## What is verified

The cursor is the point of the tool, so it is what the test exercises: a
first call reports the capture, hands back `newest_captured_at_ms`, and a
call one millisecond past that cursor reports zero records with no cursor
and no apps. A serialized response is asserted not to contain the stored
capture text.

The store test pins the subtler property: `record_count` counts every
record in the window even when `app_limit` truncates the `apps` list. A
total that shrank with the display cap would make repeated polling
under-report activity, which is the one thing a delta must not do.

## Explicitly not done

No per-record detail, no changed-versus-new distinction, and no deletion
signal. A record removed by `delete_everywhere` simply stops being counted;
a poller cannot currently tell "nothing new" from "something was removed".
That matters for a client caching results, and wants a tombstone or a
version counter rather than a bigger delta payload.

## Landmines

`since_ms` is inclusive, so passing the previous `newest_captured_at_ms`
straight back re-reports the boundary record. The schema documents feeding
the cursor back as-is, and a caller wanting strictly-newer results adds one
millisecond, as the test does. If this ever becomes a source of duplicate
work for a real client, the fix is a separate exclusive-cursor parameter,
not silently changing the existing comparison.
